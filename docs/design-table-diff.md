# 表格 Diff 三方案取舍设计文档

> 段落是一维序列,表格是二维结构。v1 的段落级 LCS 直接套不上去——
> 这一篇记录我在动手前推演过的三条路,以及为什么选中间那条。

## 方案 A:全展平(拒绝)

**做法:** 每个单元格当一个段落塞进文档序列,零改动复用 v1 算法。

**优点:** 实现成本为零。

**致命缺陷:** 插一行 → 该行所有单元格都是 inserted,**行列关系彻底丢失**;
更糟的是列插入会让所有后续单元格错位——**一维雪崩在二维上复活**。
这等于把我 v1 好不容易解决的问题原封不动搬回来。否决。

## 方案 B:分层对齐(选定)

**做法:** 表格整体作为一个 Block 参与文档级 LCS(身份 = 表头指纹);
配对上的表格再做内部 diff:行级 LCS → 单元格级比对。

**优点:**
- 结构保留:插一行只报一行,插一列只报一列;
- 复用 `seqdiff` 通用层,没有新算法;
- 与段落管线同一套心智模型:文档级粗对齐 + 局部细化。

**代价:**
- 需要回答"两份文档里的表格凭什么算同一张"(见下);
- 合并单元格处理不了——明确降级为 warning,不假装支持。

## 方案 C:二维双向 LCS(过度设计)

**做法:** 行和列各做一次 LCS,求二维最优对齐。

**优点:** 理论上最完备,行列同时增删也能最优对齐。

**致命缺陷:** 复杂度 O(m²n²);而真实修订里表格改动 90% 是改单元格内容
和增删行,列结构变了往往意味着换了一张表。为一个罕见场景付四次方的
复杂度,不划算。**这是我主动砍掉的功能,不是我做不到。**

## 方案 B 的核心设计:表格身份配对

docx 的 `<w:tbl>` 没有 ID。两层策略,按顺序尝试:

1. **表头行完全相同 → 同一张表。** 这是 `Block.key()` 用表头做指纹的原因:
   表头是表格最稳定的部分,改数据的人很少改表头。
2. **表头不同,但内容高度重叠 →** 行级 LCS 覆盖率
   `2 * lcs_len / (len(rows_a) + len(rows_b))` ≥ `TABLE_SIM_THRESHOLD`
   判为同一张表的 modified。选 LCS 覆盖率而不是 Jaccard 的原因:
   **Jaccard 对行序不敏感**——两张行序完全颠倒的表会被判成相同,而表格
   的行序是有意义的。这个度量顺手复用了 `seqdiff`。
3. **都不满足 → 老老实实报删表 + 增表。**

## 不支持的边界(说出来,比假装支持强)

- 合并单元格(`w:gridSpan` / `w:vMerge`):parser 检测到后在 Block 上打
  `fmt={"unsupported": "merged_cells"}`,渲染层在表格上方显示警告。
- 嵌套表格:行/单元格解析用 `findall`(只取直接子节点),嵌套表被忽略。
- 列插入的语义对不上:列数不同时退化为列级 LCS 对齐单元格,**但哪一列是
  "部门"的语义已经漂移**——所以插列样本(tbl_new4)的验收标准是"合理地失败":
  不崩、输出对齐可解释、给出 warning。
